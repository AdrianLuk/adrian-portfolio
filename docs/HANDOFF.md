- **Motion:** rich across the site (hero, page transitions, scroll-driven sections, small interactions), within these guardrails, which are acceptance criteria:

## Technical notes

- Next 16, React 19 and Tailwind v4 (CSS-first `@theme inline`, no `tailwind.config.js`).
- Read `node_modules/next/dist/docs/` before writing Next code (see `AGENTS.md`).
- `middleware.ts` is renamed `proxy.ts` in Next 16. The portfolio shouldn't need it.
- GSAP and motion sections are client components; everything else stays a server component. Respect `prefers-reduced-motion`.
- Accessibility bar: axe-clean, keyboard navigable, visible focus.
- No Lighthouse CI: it was removed on 2026-10-07, as it took about 10 minutes of every CI run to guard load speed, which the site now trades for motion. Accessibility is still gated by axe in `e2e/a11y.spec.ts`; layout shift is no longer checked automatically. Three.js and GSAP load after the first paint: the hero imports only `src/components/world/rigs.ts` and `src/components/lit-sites.ts` (plain data; the Lit sites read `@/content/site`) up front, the Resume page's Skyline, the Case study's court and the Rally game's court load Three.js only once their first contentful paint is in, and `e2e/performance.spec.ts` fails on any of these pages if a library is asked for before it. The Rally game's code loads only on `/play`; `e2e/play.spec.ts` fails if home asks for it, or the Case study does, even with their links to `/play` on screen (both opt out of prefetching for that reason).
- The link previews (`public/share/`), the night backdrop behind `/play` and the 404 (`public/world/valley-*`), the court still (`public/world/court-*`: the court as the camera holds it, neither dimmed nor scattered with motes, the Case study's first paint and the fallback under its live world) and the Skyline still (`public/world/skyline-*`, likewise the Resume page's) are stills of the world, photographed by `scripts/share-stills.mjs` against the production build on a machine with a GPU. Re-run it whenever the world or a share card changes; `--share`, `--valley`, `--court` or `--skyline` redraws only that set. To check a page with a world by eye, or for a pull request's before and after, `node scripts/place-shots.mjs <base-url> <path> <out-prefix>` photographs any page (desktop and phone) and, where the page has a Place, its world alone as the camera holds it there; `scripts/hero-shots.mjs` does home.
- The Contact section's portrait (`public/contact/`) is graded from `src/assets/adrian-luk.jpg` by `scripts/portrait.mjs` (sharp: nothing cut out, just the night grade, a wide feathered vignette and a cyan rim light), at the fixed sizes in `contact.portrait`. The source photo itself is never served. Re-run it whenever the photo or the grade changes.
- **One world, and transits through it.** Home, the Juice Bros Case study and the Resume page share one world: one canvas and one compiled scene kept for the whole visit (`src/components/world-host.ts`). Each of them is a Place in it (`src/components/world-places.ts`): home's settled view and scroll route, the Juice Bros court, and the Skyline. Each page claims the world with a canvas of its own, which the world's canvas stands in for, before the page paints; other pages park it behind their still backdrop. A navigation between two Places (a link, or Back and Forward) is a transit: the camera flies instead of crossfading (`src/components/world-transits.ts`, started from `onRouterTransitionStart` in `src/instrumentation-client.ts`, which also tags the navigation with `TRANSIT_TRANSITION_TYPE` from `src/components/world-places.ts` so the layout's `<ViewTransition>` skips its crossfade). A page whose data the click didn't prefetch commits in a later transition that has lost that type, so `src/app/globals.css` also turns every view transition's animation off while `[data-world-root][data-transit]` is set (a page that commits after the flight's time is up lands the camera inside its own view transition, so `data-transit` stays until that transition is over). "Flight" alone means the opening. Whether a navigation is a transit is decided from the page the router last committed to, so a navigation that never arrives changes nothing. The transit leaves from wherever the camera is: along the scroll route, at the court or the Skyline, partway through another transit (a newer navigation retargets it from there), or inside the opening, which it finishes along the opening's own path, quickened, before taking the route, so the camera never jumps. It runs along the scroll route (`src/components/world/transit.ts`), the whole trip capped at `TRANSIT_MAX_SECONDS`, and a trip to the court or the Skyline eases off the route onto that Place's pose as it lands, in three legs each paced by the way it flies: off the departure onto the route, along it, and off it onto the pose. The Skyline's landing leaves the route at the harbour's mouth and sweeps across the water to the far shore, panning about 70 degrees to face downtown at a medium speed (`TURN_REACH` keeps any landing's pan under about 150 degrees a second; the route's own swings between lit sites run near 200). On a visit that hasn't shown home, the route isn't measured yet, so a transit between the court and the Skyline runs along a nominal route for the screen's shape (`src/components/world/nominal-route.ts`): past the second Lit site the route doesn't depend on home's layout, so those legs fly as home's own would. The new page renders at once under it. While the camera flies, the world's root (`<main data-world-root>`) carries `data-transit`; while the destination's copy waits for it, `data-arriving`, which hides that copy (`arrivesAtCourt` and `arrivesAtSkyline` in `src/app/styles.ts`, the hero's own on home) with `visibility: hidden`, so it is out of reach of focus and screen readers, and lets it fade in as the camera lands, or after `TRANSIT_MAX_SECONDS` from the navigation's start, whichever comes first (the camera itself may land later if the page is slow to arrive). Focus after the navigation is the router's, as on any other page. Home reached this way lands settled, without the opening. Deliberately, a transit home lands at the stop home's own scroll puts the camera at (an anchor such as `/#work` or `/#contact`, or a restored scroll position), not at the settled view: landing at the settled view with the page scrolled would jump the camera along the route on the first scroll. At the court the camera stands still, low behind the near baseline, with the court in the lower third of the frame so the Case study's title and links sit over the sky (`courtPose` in `src/components/world/route.ts`); nothing moves it once it lands, and the pointer doesn't lean it. The Camera director blends the court's look in through the transit there and out through one leaving it (`src/components/world/court-look.ts`): its floodlights up, the fog tinted toward its violet, and a small ball rallying slowly over the net, the one thing it adds that moves. The world stays live behind the whole Case study, the pinned Player tools scene included, and with reduced motion preferred it is one still frame, with no rally ball. The one exception is a software renderer (SwiftShader, llvmpipe, or a context that fails `failIfMajorPerformanceCaveat`; `drawsInSoftware` and `holdsFrame` in `src/components/world/quality.ts`), where every frame of the world costs the whole page (the pinned scene drops from 60fps to about 15 on a fast machine, and CI's frames take about 300ms): there the court and the Skyline are each one still frame once the camera has landed, as under reduced motion, and through any Transit the world holds its frame until the page it flies to is in, so that page gets the main thread to render in and its copy can arrive with the camera. `e2e/court.spec.ts` holds the scene's frame times near parity with a run without the world. Under reduced motion (read at each navigation), without WebGL, or with the GPU context lost, nothing flies: the swap is instant, or a crossfade over the still.
- Search: `src/app/sitemap.ts` lists every route that has a link preview (`shareCards`), `src/app/robots.ts` lets every crawler in and points at it, and each route names itself as its canonical URL (the 404 names none). `www.adrianluk.com` redirects permanently to the bare domain (`next.config.ts`). Home carries WebSite and Person JSON-LD (`src/app/structured-data.ts`), built from the site's own copy, so it never claims more than the page does. The Resume page carries the same Person (one `@id`), with every Role under `alumniOf` as an `OrganizationRole`: titles, employers and ISO dates, no bullets. A new route needs a share card to be in the sitemap. `/llms.txt` is served too (`src/app/llms.txt/route.ts`), built at build time from the content module (`src/app/llms-txt.ts`), and robots stays allow-all on purpose, so AI crawlers are welcome.
- Past a 1920px screen the root font size grows at half the viewport's rate (24px at 3840 wide), so the hero's name and copy hold the frame on large monitors and TVs.
- The launch checklist and its results are in `docs/launch-checklist.md`.

## Content accuracy (important)

Take every claim from the resume or the verified experience copy. Don't embellish.

- **Control D:** the a11y overhaul covered ~248 components and has a cypress-axe WCAG 2.1 AA suite over 96 routes. The statistics panel redesign and the Gatsby-to-Next migration were colleagues' work: never credit them to Adrian.
- **Control D outcome:** the product got its SOC certification, and the a11y overhaul was Adrian's part of the work that fed into it. Word it as his contribution to a certification the company achieved, not as "he got it certified". The SOC type (2, Type I/II) isn't known, so don't state it.
- **BT Cup:** "Architected" applies only to the data model, REST API and React front end. Colleagues built the SAML SSO middleware, most of the admin panel and the scoring engine.
- **BT Cup outcome:** the number of contests and the time span are unknown, so state neither. The outcome rests on scale (11,750 provisioned and roughly 2,000 enrolled per contest, the resume's figure; an earlier ~2,180 figure is retired) and his share of the codebase.
- **Juice Bros outcome:** there are no usage numbers, and the Player tools are mainly used by Adrian himself. Never claim traffic, users or adoption. The outcome is that the site is live and shipped, and that he built the tools for his own play and uses them; the link to the live site is the proof. Its Highlight carries no key numbers: the Player tools keep growing, so never state a count, and not all are no-login.
- **Life House (Full Stack Developer, Oct 2022 to Feb 2024; from the 2026 resume):** primary frontend engineer on the guest-facing booking widget, an embeddable React and TypeScript booking flow hotels dropped onto their own sites with one script tag; scoped every generated CSS rule to the widget container with a custom Emotion stylis plugin (no Shadow DOM, no iframe); retrofitted five languages and multi-currency onto a shipped UI (88 files, 22 i18next namespaces, Contentful over GraphQL); built bulk rate editing for operators; top contributor on the revenue and marketing dashboards over an Apollo Federation gateway; backend work in a NestJS GraphQL subgraph over the Mews and Cloudbeds APIs. Describe the widget role as "primary frontend engineer" (the resume) or "top contributor", not "top committer". Never claim he built it alone.
- **Studio:** if it's ever mentioned, Adrian inherited a dormant prototype; he didn't start the project.

If a detail isn't in the resume, the verified experience copy or the project context, ask rather than invent it.
